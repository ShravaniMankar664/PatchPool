# Security and Limitations

## Contract protections present in local source

The local PatchPool contract records the creator's initial funding and additional per-wallet bounty contributions, submission identifiers and intended payee, reviewer decisions, aggregate reward release, and eligible per-contributor refunds. Its `refundableBalance` is cleared when approval makes the pool payable, even if a payee transfer later fails; the bounty remains approved and can be retried. The regression suite covers contribution totals, multi-contributor payout/refund, funding cutoff, unauthorized review/refund, submission and deadline boundaries, payout destination, duplicate settlement, failed payee transfer behavior, and the rule that an approved reward cannot be reclaimed through the refund path. These are local tests, not an independent security audit or live deployment verification.

## Assumptions and limits

- One assigned reviewer is supported; reviewer quorum, arbitration, and disputes are not.
- Multiple contributors can fund one bounty in the current source. Funding closes at the submission deadline. Contributors claim their own full contribution after expiry; the app does not yet provide an independently indexed, complete contributor roster beyond contract events.
- Frontend reads are bounded and paginated: 20 bounties per page, up to 10 latest submissions per bounty, and 2,000-block event-log ranges loaded on demand. Very old task metadata and activity require loading older event pages; RPC provider response limits may still produce a clear event-history error for a dense range.
- A Git object ID identifies a referenced revision, not its correctness.
- An evidence digest helps detect changed bytes when the source evidence is available; it does not prove the evidence is true or that tests ran.
- The frontend can compare a locally selected file against the on-chain SHA-256 digest without uploading it. The local Playwright lifecycle exercised the match and mismatch paths; this verifies byte equality only.
- The same-origin MST JSON-RPC proxy now accepts only an allowlist of read-only methods, requires JSON-RPC 2.0 request IDs, limits requests to 256 KiB, upstream responses to 4 MiB, and batches to 20 entries, and rejects transaction/signing/admin methods before forwarding. Four focused guard tests pass. It remains unauthenticated and can still be used for bounded read traffic; deployment operators should monitor and rate-limit it at the hosting layer if abuse becomes a concern.
- Human review remains the quality decision.
- The current source enforces address-level separation: the creator and all contributors cannot submit or be named as payout recipients; the reviewer cannot fund, submit, or receive a payout. A submitter or named payee cannot later fund that same bounty. These checks are in contract entry points. They do not establish real-world identity: one person can control multiple addresses.
- Task title and description are emitted in a `BountyMetadata` event, limited to 16 KiB of UTF-8, and hash-checked against the exact JSON bytes at creation. This provides cross-client discovery from chain logs, but metadata is permanently public; sponsors must not put secrets, personal data, or confidential code in it. Older deployments have no metadata event and remain incompatible with the current source ABI.
- The UI's wallet address comparison uses a public expected address for display only. It does not provide signing or deployment authority.
- When disconnected, the frontend selects Wagmi's configured default chain for public reads. Writes require a connected, identified BridgeKey provider and MST Mainnet chain ID `4646` (or the isolated local E2E provider in non-production tests). The browser test confirms wallet-free local reads without signing/transaction RPC methods.
- BridgeKey selection matches the name/ID metadata exposed by Wagmi's EIP-6963 connectors. That metadata is self-reported and does not authenticate the wallet software. No real BridgeKey session or signing transaction has been tested.
- MST Mainnet (4646) is the only production network. The verified PatchPool deployment is finalized in the active registry at block `21783933`. The historical Legacy Testnet deployment remains preserved and its frontend write gate stays off.
- BridgeKey is compulsory for deployment, but no BridgeKey provider/account was detected in this environment. Testnet signing through the private-key CLI is explicitly disabled; no private key should be configured as a substitute.
- The deployment is verified, but no live BridgeKey signing session or bounty workflow has been checked. Wallet-provider identification uses connector metadata and cannot authenticate wallet software.
- No independent security audit has been performed. A fresh production dependency audit on 30 October 2026 found 30 package findings (18 high, 12 moderate, zero critical). This is not a count of 30 independent vulnerabilities: several packages inherit the same underlying advisory through dependency chains. See the current triage below. The previous full-tree audit (29 October) is historical and was not refreshed in this review.

**Remediation proposal (not applied):** evaluate two paths in an isolated checkout after owner approval: (1) a focused PostCSS `8.5.23` override against Next's exact PostCSS pin, retaining Next 15 if the lock tree, production build, and route checks remain valid; (2) update vulnerable compatible WalletConnect leaves where parent ranges permit, then assess whether Wagmi 3.7.9 is necessary. Wagmi 3 and Next 16 are breaking-version migrations and need separate compatibility work; do not accept npm's bulk fix blindly. Also resolve Lodash `4.18.0`, `ws` `8.21.0`, decode component above `0.5.0`, UUID `11.1.1`, and Zod `4.6.6` only through compatible dependency paths. Required validation after any approved change: `npm ls`, production `npm audit`, frontend TypeScript/build/lint, RPC guard tests, and full local E2E; additionally inspect BridgeKey connector discovery and the production bundle. No dependency or lockfile changes were made in this review.

The fresh local E2E run passed five scenarios on disposable Hardhat only. It did not exercise real BridgeKey, WalletConnect, MetaMask, signing, or Mainnet writes. The optional connector import warnings do not establish that each connector runtime is reachable, but they also do not erase the vulnerable packages from the production dependency graph.
- The source is prepared on `publish/patchpool-source` for review; the existing README-only `main` branch remains unchanged until a pull request is merged. No public application, demo video, or external submission is confirmed.

## Before public release

Re-run the full supported checks, resolve or explicitly risk-accept the outstanding production audit findings, obtain a browser-based BridgeKey connection/sign/rejection test, verify the selected network and deployment bytecode, inspect Git history and staged files for secrets, and publish only after explicit authorization. Never place wallet credentials in the browser bundle or repository.
